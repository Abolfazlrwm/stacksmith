# ADR-0020: cosign image signing and SBOM attestation

- **Status:** accepted
- **Date:** 2026-11-27
- **Supersedes:** —

## Context

ADR-0019 ships multi-arch images to GHCR with build provenance
attestation. What is missing is **cosign signing**: a detached signature
that a consumer can verify without trusting GitHub's attestation
infrastructure.

The difference:

- **Build provenance** (ADR-0019) — proves "this image was built by this
  CI run from this commit". Verified via GitHub's attestation API.
- **cosign signing** (this ADR) — proves "this image was signed by this
  key". Verified offline with `cosign verify`.

Both are needed: provenance answers "who built it?", cosign answers
"who signed it?". A consumer that trusts the signing key but not the CI
platform can verify cosign without trusting GitHub.

## Decision

Add a `cosign-sign.yml` workflow that runs after the registry build
(ADR-0019). It:

1. Installs cosign.
2. Signs the image with **keyless cosign** (using the GitHub OIDC token
   as the signing identity — no key to manage).
3. Generates an SBOM with syft and attaches it as a cosign attestation
   (`cosign attest --type spdxjson`).
4. Verifies the signature (`cosign verify` with the GitHub identity
   regex).

## Rationale

- **Keyless over static keys.** A static signing key is a secret that
  must be stored, rotated, and protected. Keyless cosign uses the GitHub
  OIDC token as the signing identity — no key to leak, no rotation
  needed. The signature is tied to the GitHub repository and workflow.

- **cosign attest for SBOM.** The SBOM is already generated by Buildx
  (ADR-0019) and by syft (ADR-0017). The cosign attestation attaches it
  as a signed predicate to the image, so a consumer can verify both the
  image signature and the SBOM signature in one step.

- **Verify after sign.** The workflow verifies the signature immediately
  after signing. This catches a misconfiguration (wrong identity regex,
  expired token) before the image reaches a consumer.

- **Runs only on main and tags.** PR builds do not push to the registry
  (ADR-0019), so there is nothing to sign. The sign workflow triggers
  only when the registry-build workflow has pushed an image.

## Considered alternatives

### Static signing key

Rejected. A static key requires a secret in GitHub, rotation, and
protection. Keyless cosign achieves the same trust guarantee with zero
key management. If a consumer requires a static key (e.g. for offline
verification without GitHub access), cosign supports both — the
keyless signature is the default; a static key can be added later.

### Notary v2

Not rejected, but cosign is the standard for Sigstore (the supply-chain
project under the OpenSSF umbrella). Notary v2 is an alternative; the
choice is not load-bearing. cosign has better GitHub Actions integration.

### GitHub attestation only (no cosign)

Rejected. GitHub's build provenance attestation is valuable but ties
verification to GitHub's API. cosign verification is offline and works
with any registry. Both layers are defense in depth.

## Consequences

- `cosign-sign.yml` runs on push to `main` and on tags (`v*`), after
  `registry-build.yml` has pushed the image.
- The image is signed with keyless cosign (GitHub OIDC identity).
- An SBOM is generated with syft and attached as a cosign attestation.
- The signature is verified immediately after signing.
- A consumer can verify with:

  ```bash
  cosign verify --certificate-identity-regexp \
    "https://github.com/Abolfazlrwm/stacksmith/.github/.+" \
    --certificate-oidc-issuer "https://token.actions.githubusercontent.com" \
    ghcr.io/abolfazlrwm/stacksmith/app:latest
  ```

- The workflow requires `id-token: write` and `attestations: write`
  permissions for the OIDC token and attestation push.

# ADR-0021: Terraform provisioning for the VPS

- **Status:** accepted
- **Date:** 2026-11-28
- **Supersedes:** the "manual VPS setup" assumption from ADR-0001

## Context

Every previous phase assumes the VPS exists and Docker is installed.
The operator has to manually provision a server, open firewall ports,
install Docker, and clone the repo. This is undocumented infrastructure
— if the VPS is lost, rebuilding it is a manual process.

## Decision

Ship a Terraform module that provisions a Hetzner Cloud VPS with:

- The firewall rules (SSH 22, HTTP 80, HTTPS 443, monitoring 3000).
- A cloud-init script that installs Docker, clones the repo, and sets
  up UFW.
- A generated `deploy-to-vps.sh` script that SSHs in and brings up the
  stack.

## Rationale

- **Hetzner Cloud as the default.** Cheapest VPS offering for a
  single-host deployment (cx22: 2 vCPU / 4 GB for ~€4/month). The module
  is provider-agnostic; swapping to DigitalOcean or AWS requires
  changing only the provider block and the server resource.

- **cloud-init for bootstrap.** The VPS boots with Docker installed and
  the repo cloned. No manual SSH for the initial setup. The operator
  edits `.env` on the server and runs `make up`.

- **Firewall as code.** The firewall rules are in Terraform, not in a
  runbook. Changing a rule is a `terraform apply`, not a manual `ufw`
  command.

- **Generated deploy script.** Terraform writes
  `scripts/deploy-to-vps.sh` with the server IP baked in. The operator
  runs it after `terraform apply`.

## Considered alternatives

### Manual VPS setup (v0.4 behavior)

Rejected for v0.5. The manual process works but is not reproducible. A
lost VPS requires rebuilding from memory. Terraform makes the
infrastructure a versioned artifact.

### Ansible instead of Terraform

Not rejected, but Terraform handles the provisioning (server, firewall,
DNS) and Ansible handles the configuration (packages, users). For a
single VPS with cloud-init, Terraform alone is sufficient. Ansible is
the right tool if the configuration becomes complex (multiple users,
cron jobs, logrotate).

### Kubernetes (again)

Rejected (ADR-0001).

## Consequences

- `terraform/main.tf` provisions a Hetzner Cloud VPS.
- `terraform/cloud-init.yml` installs Docker and clones the repo on
  first boot.
- `terraform/deploy-to-vps.sh` is generated by Terraform and SSHs in.
- The operator runs:

  ```bash
  cd terraform
  terraform init
  terraform apply -var="hcloud_token=..." -var="ssh_key_name=..."
  ```

- The VPS is provisioned, Docker is installed, the repo is cloned, and
  the firewall is open. The operator SSHs in, edits `.env`, and runs
  `make up`.

# ADR-0022: Chaos engineering drill

- **Status:** accepted
- **Date:** 2026-11-29
- **Supersedes:** —

## Context

Every previous drill tests the happy path or a single failure mode
(canary failure, backup failure, cert expiry). None tests whether the
stack actually recovers from a random container kill — the most common
real-world failure (OOM kill, segfault, docker daemon hiccup).

## Decision

Add a `chaos-drill.yml` workflow that:

1. Brings up the stack.
2. Verifies baseline health.
3. Kills the worker container (`docker kill`).
4. Verifies the app still serves `/health/live/` with the worker down.
5. Waits for the worker to restart (`restart: unless-stopped`).
6. Kills nginx.
7. Verifies nginx restarts and serves again.

## Rationale

- **`docker kill` is the real failure.** A container that OOMs or
  segfaults is killed by Docker. The `restart: unless-stopped` policy
  should restart it. The drill proves it does.

- **App serves with worker down.** The worker processes background jobs;
  it does not serve HTTP. The app should keep serving `/health/live/`
  with the worker down. If it does not, there is a coupling bug (the app
  depends on the worker for health, which is wrong).

- **nginx restarts after kill.** nginx is the single point of entry. If
  it dies and does not restart, the stack is down. The `restart:
  unless-stopped` policy should restart it. The drill proves it.

- **Not a full chaos suite.** This is two kills (worker, nginx), not a
  randomized chaos monkey. A full chaos suite (Litmus, Chaos Mesh) is
  Kubernetes-native and not justified for a single VPS. The two kills
  cover the most common failure modes; the operator can run more
  kills manually.

## Considered alternatives

### Litmus / Chaos Mesh

Rejected. Both are Kubernetes-native. For a single VPS with compose, a
shell script that `docker kill`s a container is the right weight.

### Random container kill

Not rejected, but not the default. A deterministic kill (worker, then
nginx) is reproducible and debuggable. A random kill is more realistic
but harder to debug when it fails. The operator can extend the script
to kill a random service.

### No chaos testing (rely on restart policy)

Rejected. The restart policy is a config; the drill is the proof. A
config that says `restart: unless-stopped` but does not actually restart
is a bug that the drill catches.

## Consequences

- `chaos-drill.yml` runs on every push.
- The drill kills the worker and nginx in sequence, verifying recovery.
- The drill adds ~2 minutes to CI (two kill+restart cycles).
- This does not replace the health-probe or canary drills; it tests a
  different failure mode (container death, not bad deploy).
