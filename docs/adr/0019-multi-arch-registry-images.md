# ADR-0019: Multi-arch registry images with GHCR and build provenance

- **Status:** accepted
- **Date:** 2026-11-26
- **Supersedes:** the "build locally" approach from Phase 1

## Context

v0.4.0 builds the app image locally on every CI run and on the VPS. This
works but has three problems:

1. **No registry.** The image exists only on the build machine. A deploy
   requires a local build, not a pull. There is no image history, no
   rollback to a previous image by digest, no vulnerability scan against
   a specific pushed tag.

2. **Single architecture.** The Dockerfile builds for `linux/amd64` only.
   An ARM64 host (AWS Graviton, Apple Silicon, Oracle Cloud ARM) cannot
   run the image.

3. **No provenance.** There is no cryptographic proof that a given image
   was built from a specific commit by a specific CI run. A compromised
   registry could swap the image without detection.

## Decision

Add a `registry-build.yml` workflow that builds and pushes the app image
to GitHub Container Registry (GHCR) with:

- **Multi-arch** (`linux/amd64` + `linux/arm64`) via Docker Buildx + QEMU.
- **SHA-tagged** images (`sha-<short>`) alongside `latest` and semver tags.
- **Build provenance attestation** via `actions/attest-build-provenance`,
  pushed to the registry as a signed attestation.
- **SBOM** generated by Buildx's `--sbom` flag, attached to the image.
- **GitHub Actions cache** (`type=gha`) for fast incremental builds.

The Dockerfile is rewritten as a **multi-stage build**: stage 1 installs
dependencies into a disposable prefix; stage 2 copies only the runtime
files. The runtime image is ~40% smaller (no build-essential, no
compiler) and includes a `HEALTHCHECK` instruction.

The compose file gains an `APP_IMAGE` env var. Set it to
`ghcr.io/abolfazlrwm/stacksmith/app:latest` to pull from the registry
instead of building locally.

## Rationale

- **GHCR over Docker Hub.** GHCR is free for public repos, uses the
  existing GitHub credentials, and has no rate limits for the repo owner.
  Docker Hub has aggressive rate limits and a separate auth system.

- **Multi-arch via QEMU.** QEMU emulation is slower than native builds
  but works in a single GitHub Actions runner. The build takes ~3 min for
  amd64 and ~6 min for arm64 (emulated). For production speed, a
  matrix build on native runners is possible — deferred to v0.6.

- **SHA tags, not just `latest`.** `latest` is mutable; a SHA tag is
  immutable. The deploy script can pin to a specific SHA for reproducible
  deploys. The release manifest (Phase 2, `scripts/release.sh`) records
  the SHA tag.

- **Build provenance attestation.** GitHub's `attest-build-provenance`
  action creates a signed attestation that records the source commit,
  the workflow run, and the build command. A consumer can verify the
  image was built by this repo's CI, not injected. This is the supply-
  chain baseline required by SLSA Level 3.

- **Multi-stage Dockerfile.** The builder stage installs build-essential
  and compiles psycopg. The runtime stage copies only the compiled
  `.so` files and Python packages. The final image has no compiler, no
  headers, no build cache — a smaller attack surface and a smaller pull.

- **`APP_IMAGE` env var.** The compose file defaults to
  `stacksmith/app:latest` (local build) but accepts `APP_IMAGE` to pull
  from the registry. This lets the operator choose: build locally for
  development, pull from GHCR for production.

## Considered alternatives

### Docker Hub

Rejected. Rate limits, separate auth, and the image is not co-located
with the source. GHCR is the right choice for a GitHub-hosted repo.

### Single-arch with a note

Rejected. ARM64 hosts are increasingly common (Graviton, Apple Silicon).
Shipping an amd64-only image in 2026 is a bug, not a limitation.

### cosign signing (Phase 9.2)

Not rejected — cosign signing is Phase 9.2. This ADR covers the registry
and multi-arch; the signing and SBOM attestation via cosign is the next
step. GitHub's build provenance attestation is the baseline; cosign is
the verifiable layer on top.

### ko (Go-only) or buildah

Rejected. ko is Go-only. buildah is more flexible but does not have
native GitHub Actions integration or multi-arch support as clean as
Buildx.

## Consequences

- `registry-build.yml` runs on push to `main`, on tags (`v*`), and on
  PRs that touch `app/` or the workflow itself.
- On PRs, the image is built but not pushed (to avoid polluting the
  registry with unreviewed code).
- On push to `main`, the image is tagged `latest`, `main`, and
  `sha-<short>`.
- On tag (`v*`), the image is tagged `v*.*.*`, `v*.*`, and `latest`.
- The image has build provenance attestation and SBOM attached.
- The Dockerfile is multi-stage; the runtime image is smaller and has a
  `HEALTHCHECK`.
- `docker-compose.prod.yml` accepts `APP_IMAGE` to override the image.
- `.env.example` documents the `APP_IMAGE` var.
- Local builds still work (`docker compose build app-blue`) — the
  registry is additive, not a replacement.
